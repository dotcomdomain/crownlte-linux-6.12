## 1. Why, and what changes

The hardware result of S1a: big C2 on cpu4-7 works (83-85 % residency at screen off,
about 64k entries in 8 min, 0 losses). Three LITTLE cores cycling C2 still lose a core
in EL3 (q22b, q40, q43, c2diag-a/b): CPU_SUSPEND never returns, and an SGI raised while
the core is in firmware is never handled.

4.9 runs C2 on all four LITTLE cores without losses. Its tick setup differs from 6.12:

| | 4.9 | 6.12 S1a | 6.12 S2 r1 (this branch) |
|---|---|---|---|
| per-CPU tick device | MCT local timer `mct_tickN` (L0-L7, SPI 470-477), rating 500, every CPU | arch timer (stops in C2, C3STOP) | LITTLE 1-3: MCT local timer `mct_tickN`, rating 500, from the C2 boot arming (45 s). CPU0, big 4-7: arch timer (as S1a) |
| timer wake of a core in C2 | that core's own SPI | IPI_TIMER from the G0 broadcast handler on CPU0; one SGI can target several cores | LITTLE 1-3: that core's own SPI. Big: IPI_TIMER from G0 (as S1a) |
| tick broadcast | registered (`mct-comp`), 0 broadcast IPIs | G0 `mct-bc`, every C2 timer wake | G0 `mct-bc`, big C2 timer wakes only |
| arch timer | clocksource only (`use-clocksource-only`) | clocksource + tick | clocksource + sched_clock everywhere; tick of CPU0 and big; on LITTLE 1-3 its clockevent loses to rating 500 and stays detached (the fallback of section 1.1 item 5) |
| HZ | 100 | 250 | 250 (section 5) |
| CPU0 C2 | yes | no | no |

Design hypothesis H1: the multi-target broadcast SGI wakes two or three LITTLE cores in
the same cycle and loses a per-core race in EL3's warm-boot path. S2 removes that wake
pattern for the LITTLE cores the way 4.9 does (design X2), so it is both the candidate
fix and the H1 test. The big cores keep the S1a wake path, which has run 64k big C2
entries without a loss, and the G0 broadcast now targets only big cores. One SGI to
several big cores is the S1a pattern that worked.

**Mixed per-CPU tick devices and the broadcast.** The tick core handles them per CPU.
When a local timer (no C3STOP, `CLOCK_EVT_FEAT_PERCPU`) becomes a CPU's tick device,
`tick_device_uses_broadcast()` clears that CPU from the broadcast masks, and
`tick_broadcast_enter()` returns 0 at once for it. The C2 state's
`CPUIDLE_FLAG_TIMER_STOP` therefore costs nothing there. The arch timer CPUs keep
C3STOP and enter the G0 oneshot broadcast in C2 as on S1a. PERCPU keeps the local
timers from ever becoming the broadcast or the oneshot-wakeup device. When a local timer
is replaced (section 1.1 item 5), `tick_setup_device()` with the arch timer puts that
CPU back under the broadcast. The G0 device stays bound to CPU0, which never enters C2.

### 1.1 exynos9810-mct-bc (DT `samsung,mct-local-timers`)

The brief named `drivers/clocksource/exynos_mct.c`. That driver stays unused on 9810
on purpose (`exynos9810.dtsi`, mct-bc header comment): its `TIMER_OF_DECLARE` probe
runs from `time_init()` and panics on any clock or write failure, which on a RECOVERY
trial is a boot loop. It also takes over sched_clock. The local timers were therefore
added to `exynos9810-mct-bc`, as design X2 says ("extend exynos9810-mct-bc with
L0-L7"). The register sequences are the 4.9 `exynos_mct.c` ones, not upstream's.

Without the property nothing changes: every existing DTB (int6, S1a, the drills)
behaves as before. The control S1a and int6 DTBs rebuilt from this tree are
byte-identical (283b1243, c30c8d04).

With the property, in probe, after the G0 broadcast passed its own self-check, only
**resources** are prepared. The `reg` window must reach 0xa44 (L7 = 0x300 + 0x700,
WSTAT at +0x40). Interrupts are read in the 4.9 order: index 0-3 = G0-G3, index 4 + N =
L<N>. Each timer is stopped (TCON write checked), masked and acknowledged. Then its IRQ
is requested as `mct_tickN` with
`IRQF_TIMER | IRQF_NOBALANCING | IRQF_PERCPU | IRQF_NO_AUTOEN`. A missing IRQ or a failed
stop leaves that CPU on the arch timer. Nothing is tested or registered at probe, and
every CPU keeps the arch timer + broadcast until cpuidle asks for the takeover:

```
exynos9810-mct-bc: local timers prepared (stopped, masked, IRQs requested, not enabled); takeover only on request by cpuidle, for the LITTLE CPUs it arms; IPI_TIMER irq <n>
```

`exynos9810_mct_local_takeover(want, ops, active)` runs once per boot from the cpuidle
boot arming work (process context), after cpuidle persisted the local-timer session
(section 1.2). CPU0 is always dropped from `want`.

1. **Self-check per requested online CPU** before anything registers. Route L<N> to
   CPU N, write TCNTB = 1, then three one-shot events of 10 ms (130000 counts at
   13 MHz). Each must:
   - arrive within 100 ms;
   - be taken on CPU N;
   - clear;
   - have its stop write in the ISR acknowledged (and the final stop after the rounds);
   - come 260000 ± 2 % MCT clocks (+ 1 ms late margin) after the start. This proves
     the 4.9 rate (counter steps every TCNTB + 1 = 2 MCT clocks) against the FRC, which
     the G0 check already proved equal to the arch counter.

   A CPU that fails keeps the arch timer and the broadcast.
2. **Registration** through cpuhp `CPUHP_AP_EXYNOS4_MCT_TIMER_STARTING` (unused: no
   `samsung,exynos4210-mct` node). It runs on each online CPU with IRQs off, and at
   every later online. It does something only for a CPU that passed the self-check
   and whose timer has not failed:
   - 4.9 `exynos4_mct_starting_cpu()`: TCNTB = 1 and force affinity. A failure there
     rejects the timer before registration (`rejected`, the arch timer stays). Then
     enable_irq;
   - `clockevents_config_and_register()` at MCT rate / 2, min 0xf, max 0x7fffffff,
     rating 500, `PERIODIC | ONESHOT | PERCPU`.

   PERCPU is the upstream flag. It keeps the device from ever becoming a broadcast
   device: at rating 500 it would otherwise replace G0. The tick core prefers it over
   the arch timer (450), so it becomes the CPU's tick device (see "Mixed per-CPU tick
   devices" above). Afterwards each tested CPU must really tick on its local timer;
   the result line lists them:

   ```
   exynos9810-mct-bc: local timers: takeover of 1-3: self-check passed on 1-3 (start->irq <a>..<b> MCT clocks, expected 260000 for 10000 us at 13000000 Hz), tick device now on 1-3; rating 500, every other CPU keeps the arch timer + broadcast; IPI_TIMER irq <n>
   ```
3. **Runtime**, the 4.9 sequences:
   - `set_next_event`: ICNTB = cycles | update bit, INT_ENB = 1, TCON = INT_START |
     TIMER_START (+ INTERVAL in periodic). TCON is not started after an ICNTB failure;
   - ISR: INT_CSTAT = 1, then stop TCON unless periodic, then the event handler;
   - shutdown: stop; resume: stop + TCNTB = 1;
   - dying CPU: stop, disable_irq_nosync, mask + ack.
4. **Every synchronised write is checked** (TCNTB, ICNTB, TCON; 4.9 panicked instead).
   After registration, a write that is not acknowledged, or an interrupt that stays
   pending after the ack (polled briefly, then masked, then the IRQ is disabled), is a
   **fault**. Faults can come from set_next_event, shutdown/oneshot-stopped, periodic,
   resume, the ISR stop and CPU dying. On the timer's own CPU, in that context
   (`mct_l_fault()`, no printk):
   - the timer is latched `failed` for the rest of the boot. That store is the LITTLE
     C2 gate: `exynos9810_mct_local_active()` is false from then on, so every later
     LITTLE C2 entry on that CPU runs WFI (`no_ltimer`). The same CPU wrote the latch,
     so program order is enough;
   - `set_next_event()` returns `-EIO` at once from then on and never touches the
     hardware again. A programming that did not happen is never reported as done. The
     tick core retries a bounded number of times (each retry fails at once), then
     gives up until the replacement;
   - the fault count rises (cpuidle refuses LITTLE arming from that moment and blocks
     the session close until the fault is in the record), and an irq_work queues the
     recovery work on CPU0.
5. **Recovery** (`mct_l_fault_fn()`, process context, CPU0, after any takeover in
   progress):
   1. `mct_tickN: local timer FAULT on cpuN: <why> ...` (KERN_EMERG);
   2. cpuidle `ops->fault`: LITTLE C2 disarmed on every LITTLE CPU for the rest of the
      boot, then flag LTIMER (reason `ltimer`) written into the record and read back.
      This comes before the replacement, which could hang;
   3. synchronised replacement: `clockevents_unbind_device()` runs on that CPU under the
      clockevents lock and installs that CPU's detached arch timer (the only detached
      device that serves it alone). `tick_setup_device()` carries over the pending
      expiry and puts the CPU back under the G0 broadcast. Then the local timer is
      masked at the MCT and its IRQ disabled for good;
   4. success: `mct_tickN: cpuN ticks on arch_sys_timer now (local timer replaced) ...`.
      The timer never registers again on this boot, hotplug included;
   5. failure (unbind error, or the local timer is still the tick device): cpuidle
      `ops->fatal`. The session stays open (next boot UNCLEAN + LTIMER), deep idle goes
      off, everything is disarmed, then the watchdog final stop, `orderly_reboot()`, and
      `emergency_restart()` 75 s later as the last resort.

`exynos9810_mct_local_active(cpu)` is true when the CPU's tick device is its local timer
now and the timer has not failed. It reads the tick device through the
`tick_cpu_evtdev()` accessor, an 11-line addition to `kernel/time/tick-common.c`.
`exynos9810_mct_local_faults()` returns the number of latched faults (any context).

### 1.2 cpuidle-exynos9810 (DT `samsung,c2-little-local-timer`)

- **Local-timer session.** The boot arming work (45 s) first runs the takeover, once
  per boot, if the MCT broadcast is ready. `want` is the pending boot-arming CPUs of
  cluster 0 without CPU0, so 1-3 in this DTB. Under `e9810_arm_lock` it checks the
  same conditions as an arming: setup, the record page, no shutdown, no all/LITTLE/LTIMER
  quarantine, LITTLE enabled, deep idle on, no loss, no kill switch, no fault yet.
  Then it writes session **LT_ARMED** into the record and reads it back. Only then
  does it call `exynos9810_mct_local_takeover()`. If the write fails, there is no
  takeover and the LITTLE CPUs are not armed:

  ```
  exynos9810-cpuidle: C2 local-timer session persisted (record seq N, LT_ARMED): MCT local timer takeover of 1-3 (CPU0 and big keep the arch timer + broadcast)
  exynos9810-cpuidle: MCT local timer takeover: 1-3 tick on their local timer
  ```
- LT_ARMED covers an armed C2 session: the following arming keeps it (no downgrade to
  ARMED). The shutdown drain moves it to **LT_SHUTDOWN**, and only the last controlled
  point of a restart, halt or power-off closes it to IDLE (record v4, section 8). Any
  other end of the boot leaves LT_ARMED or LT_SHUTDOWN, and the next boot adds
  **LTIMER** to UNCLEAN: no takeover, all C2 off.
- The session is never closed (drain and final point refuse) after the fatal path,
  after a failed fault record, while a latched fault is not yet in the record, or
  while the takeover runs.
- Flag **LTIMER** in force: no takeover and no LITTLE arming
  (`C2 quarantined (LITTLE, local timers): ...`, boot arming reduced to 4-7). Big C2
  stays allowed unless another flag says otherwise. Only a token or root clears it.
- Arming a LITTLE CPU is refused (final) unless `exynos9810_mct_local_active(cpu)`
  (`C2 boot arming of cpuN refused: LITTLE C2 needs the CPU's tick on its MCT local timer ...`),
  or once any local timer fault was latched on this boot
  (`LITTLE C2 off: an MCT local timer failed on this boot`).
- Every LITTLE C2 entry checks `exynos9810_mct_local_active()` again. If false, the
  entry is counted as `no_ltimer` and runs WFI. This covers a fault latched since the
  last arming check, and hotplug.
- Big cores need nothing new: they tick on the arch timer and wake through the G0
  broadcast (the validated S1a path).
- `c2 stats:` lines and `c2_stats` gain `ltimer=0|1 no_ltimer=N` per CPU and
  `ltimer_faults=N` (sysfs also `ltimer_close_blocked`). `c2_quarantine` shows
  `version=` and `ltimer`.
- **Unchanged:** the lost-core detector, the watchdog final stop, the drain, trial
  tokens, drills, the arming order and retries, and the CPU0 refusal.

## 4. Trial (ROM-RAM), PASS lines, failure signatures

**Order.** The phone's record is trusted and clean after the S1a run (it survived the
4.9 bounce; floor 0xc2c20001; format v3, which this kernel still reads). Boot this pack
next, with no cold boot in between.
- The token then makes a one-shot "clear" of flags 0x0 and becomes the floor
  (0xc2c20004). The first write turns the record into v4.
- On a cold-booted or damaged page it is spent without clearing. Nothing arms then
  (`C2 quarantined (all) ... UNINIT`), and you need a new token above 0xc2c20004, or a
  drill (a) boot first, then a new pack.
- Do not boot a v3-only kernel (S1a `int6-c2-r2`, drill (a) r2) between two S2 r1
  boots: it reads the v4 slots as invalid and fails closed (UNINIT, its own token
  spent). Afterwards a new token is needed.

Run the standard int6 ROM-RAM soak (c2-runtime.md 3.2): 15 min screen on, 30 min screen
off (Wi-Fi associated), 15 min load. Take a snapshot every 60 s (section 6). End with
the DONE frame.

- per CPU at each `c2 stats:`: resumed + early + psci_fail = enter (or enter - 1 for a
  CPU in `firmware` at that moment);
- `ltimer=1 no_ltimer=0` on cpu1-3; `ltimer_faults=0`;
- psci_fail = 0 on the big cores; on cpu1-3 only -22, below 1 % of entries;
- `/proc/interrupts` (section 6): the `Timer broadcast interrupts` row stays constant in
  the cpu1-3 columns (it counts on 4-7: big C2 wakes, as S1a). `mct_tick1..3` count up.
  `mct_tick0` and `mct_tick4..7` stay 0. `mct-bc` counts (big C2);
- residency at screen off (section 6): cpu1-3 C2 ≥ 79 % (within 5 points of 4.9's
  84 %, the design's efficiency gate); cpu4-7 ≥ 85 % (S1a: 83.5-85 %);
- the DONE reboot logs both session lines (LT_SHUTDOWN, then LT_SHUTDOWN -> IDLE), and
  a further boot of the same pack logs
  `trial token 0xc2c20004 not above the trial floor 0xc2c20004 ... ignored`, then
  `clear`, takes over 1-3 again and arms 1-7 again.

Design S2 target (4.2): little-3 for ≥ 10 min (≥ 150k LITTLE cycles) with 0 lost, then
ROM-RAM 60 min. At 4.9 rates (79-109 entries/s per LITTLE core), 30 min screen off gives
about 3 × 85 × 1800 ≈ 460k LITTLE C2 cycles.

### 4.3 Where S2 sits among the design's five tests (2.4)

- **X2 (per-CPU MCT local timers) is what this build implements**, under real Lineage
  load instead of the delayed-UFS self-test phase. A clean soak means H1 was the
  trigger: the multi-target broadcast SGI, not three LITTLE cores in C2 as such.
- X1 (staggered single-target broadcast), X3 (CPU0 kept out of WFI), X4 (LITTLE
  frequency pinned) and X5 (resume marker in a no-map page) are **not** built. They are
  the next diagnostics only if S2 still loses a LITTLE core:
  - X5 first: it tells EL3 from early `cpu_resume`;
  - then X3 and X4 on top of S2.
- The design's further S2 step, little-4 (CPU0 in C2, the full 4.9 parity), is not in
  this DTB (the brief keeps CPU0 out). It needs the CPU0 refusal lifted in the driver
  (CPU0 also runs the lost-core detector work and takes the G0 interrupt, so that
  needs a review of its own) and a new DTB with a new token.

## 5. HZ stays 250

The design names HZ 250 against 100 as a minor contributor to H1: more jiffy-aligned
expiries per second, each one a multi-target broadcast. Its fix (X2) does not change HZ,
and S2 keeps 250:
- with their local timers the LITTLE cores get no broadcast fan-out for HZ to
  multiply (the big cores keep the S1a broadcast, which never lost a core);
- with NO_HZ_IDLE an idle CPU has no periodic tick at all.

HZ now only sets the busy-CPU tick rate and the timer-wheel granularity (4 ms instead
of 10 ms). Changing it would retime every subsystem of the int6 stack, all tested at
250, and would put two variables into one trial: a loss would no longer point at either.
If S2 still loses a LITTLE core, an S2b with `CONFIG_HZ_100` (one config change, same
DTB rules, a new token) is the cheap next step, next to X5.

## 6. Measuring LITTLE C2 residency against 4.9 (adb, read-only)

Use the scripts of c2-runtime.md section 4 (identical sysfs on both kernels; state1 =
C2). Git Bash: `export MSYS_NO_PATHCONV=1`. Screen off ≥ 2 min, ≥ 10 min after boot,
Wi-Fi associated, same battery band. Take three 60 s windows per kernel.

```sh
snap() { adb shell 'cat /proc/uptime; for c in 0 1 2 3 4 5 6 7; do for s in /sys/devices/system/cpu/cpu$c/cpuidle/state*; do echo "cpu$c $(basename $s) $(cat $s/usage) $(cat $s/time)"; done; done' | tr -d '\r'; }
A=$(snap); sleep 60; B=$(snap)
paste <(echo "$A") <(echo "$B") | awk 'NR==1{dt=$3-$1; next} {printf "%s %s usage/s=%.1f residency=%.1f%%\n", $1, $2, ($7-$3)/dt, ($8-$4)/(dt*1e4)}'
```

Interrupts, twice 60 s apart (world-readable on both kernels):

```sh
adb shell 'cat /proc/uptime; grep -E "mct_tick|mct-bc|Timer broadcast|Rescheduling|Function call" /proc/interrupts'
```

- `mct_tick1..3` (one row each, the count in that CPU's column) must count up on
  6.12 S2 r1 as on 4.9. `mct_tick0` and `mct_tick4..7` stay 0 (those CPUs keep the arch
  timer; 4.9 counts all eight).
- `Timer broadcast interrupts` must not move in the cpu1-3 columns (4.9: 0 everywhere).
  It counts in the cpu4-7 columns (big C2 wakes, as on S1a).
- `mct-bc` (SPI 466) counts (the G0 broadcast for big C2, as on S1a).
- On S1a the LITTLE columns did not matter (LITTLE C2 was off), and `mct_tick` did not
  exist.

| | 4.9 reference (design section 3, screen off, USB) | S2 gate |
|---|---|---|
| cpu1 / cpu2 / cpu3 C2 % | 84.5 / 84.3 / 84.3 | ≥ 79 % each |
| cpu1 / cpu2 / cpu3 C2 entries/s | 87 / 79 / 81 | same order (tens to ~110/s) |
| cpu0 | 84.3 % C2, 109/s | **not comparable**: CPU0 stays WFI on S2 (state1 = 0) |

S2's LITTLE entries/s may run somewhat higher than 4.9's, because HZ 250 ticks a busy
CPU 2.5 times as often. The residency gate is what counts. For power, use the proxies of
the design section 4.4 (inline VBUS meter, or the FG current in a steady charger state),
the same on both kernels.

## 7. Risks and limits

- **H1 may be wrong.** Then a LITTLE core is lost during the soak. S0 handles it
  (detector → record → watchdog final stop → reset within about 30 s → the shim bounces
  to Lineage). The next 6.12 boot keeps **all** C2 off and takes no local timers
  (UNCLEAN + LITTLE + LTIMER: the session of a loss is never closed). The token is spent:
  a further trial needs a new pack with a token above 0xc2c20004.
- **MCT local timers are new on 6.12 hardware.** The self-check covers delivery, CPU,
  acknowledge, write status and rate per CPU before registration. It cannot cover
  behaviour inside C2. 4.9 shows that works on this SoC; on 6.12 only the G0 comparator
  (whose interrupt goes to CPU0, which never sleeps in C2) has run so far.
- **What a local timer fault guarantees, and what not.**
  - Guaranteed by the code: the failed timer's CPU stops entering C2 from that moment
    (latch on its own CPU), its programming reports failure, LITTLE arming is refused
    from the latch on, and the session cannot be closed until LTIMER is in the record.
    LT_ARMED is in the record (read back) before any local timer was touched, so
    **every** end of that boot except the clean final point gives the next boot
    UNCLEAN + LTIMER (no takeover, all C2 off). The trigger can be a panic, a watchdog
    reset, a power loss or anything else.
  - Expected but not exercised: the recovery work runs on CPU0, the record write
    succeeds, and `clockevents_unbind_device()` replaces the timer by the arch timer
    (the upstream sysfs `unbind_device` path, untested on this SoC). A failed
    replacement takes the fatal path (watchdog final stop, tested by drill (a)).
  - **Not guaranteed:** that a failing timer always ends the boot. If the work cannot
    run (CPU0 wedged) or the unbind IPI never returns, the reset depends on the buddy
    hard-lockup detector (a CPU without a working tick stops its watchdog hrtimer; its
    buddy should panic within about 12-24 s, `panic=30`) or on the CL0 watchdog (CPU0
    wedged). Round 0 claimed "stuck IRQ → panic → UNCLEAN" as a certainty. Only the
    "→ UNCLEAN on the next boot, whenever the boot ends uncleanly" part is guaranteed.
  - A timer that stops interrupting while its writes still complete is not a "fault" in
    this sense. Its CPU loses its tick silently, with the same buddy-detector
    expectation. The usage window reports it (`no local irq`, FAIL), but only every
    10 min.
- **Each local programming costs three APB writes, two with write-status polling** (as
  4.9). Only on LITTLE 1-3 now. A write that never confirms costs up to
  `MCT_WSTAT_POLLS` reads once, then the timer is failed and costs nothing more.
- **Mixed mode is new.** CPU0 and big keep exactly the S1a tick setup (arch timer + G0
  broadcast). Only the LITTLE cores leave the broadcast. The tick core supports
  per-CPU devices of different kinds (section 1). The broadcast now serves only big
  cores, a subset of S1a's pattern.
- **Takeover at 45 s instead of `time_init()`**: the LITTLE ticks switch devices at
  runtime through `cpuhp_setup_state()` (STARTING callbacks run on each CPU with IRQs
  off) while the system is up. Round 0 did the same at probe (about 1 s).
- **Record v4** is read by this kernel only. Older 6.12 kernels (S1a r2, drill (a) r2)
  read a v4 record as invalid and fail closed (section 4, Order).
- `tick_cpu_evtdev()` is a small non-upstream addition to the tick core (a read of
  `tick_cpu_device.evtdev`).
- The IPI_TIMER count assumes arm64 IPI n = SGI n (IPI_TIMER = 4, 6.12 smp.c). If not
  found, the window line says `IPI_TIMER not found` and FAIL; nothing functional
  depends on it. `/proc/interrupts` is the independent check.
- Not exercised: CPU hotplug (cpuhp re-registration; a fault inside a STARTING callback
  queues its irq_work on a CPU that is coming up), system suspend/resume
  (`tick_resume`), the periodic mode (the takeover happens after the switch to
  high-res), the fault, replacement and fatal paths.
- CPU0 never enters C2 (as S1a), so SICD (S4) remains impossible, and the 4.9 CPU0 row
  is not comparable.
- Not reviewed (Sol) for fix round 1 yet; build-only.
